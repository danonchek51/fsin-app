# Проектный контракт исполнения

## Старт каждой сессии

1. Прочитай `AGENTS.md`, `control/WORKSPACE-PROFILE.yaml` и `control/NOW.yaml`.
2. Прочитай последний handoff, только если на него указывает `NOW.yaml`; затем открой только `next_action.input_paths` и контракты, на которые они ссылаются.
3. Выполни текущий пользовательский результат из `next_action`. Команда, проверка, commit, push, уточнение или переход фазы — внутренние шаги, а не новая работа сами по себе.
4. Не начинай соседний workflow или независимую задачу по собственной инициативе.
5. Если не хватает существенного решения владельца, задай один короткий вопрос в том же чате. `blocked` и новый `ask-owner` создавай только когда это состояние должно пережить текущий чат.

## Владение данными

- `control/NOW.yaml` хранит только active work, pointers (`source_memlog` → `source_contract` → `implementation_contract`) и один action; не копируй в него requirements, lifecycle или backlog.
- `bmad-spec` workspace владеет source contract: `.memlog.md` — журнал решений, `SPEC.md` и companions — производный контракт.
- BMM implementation spec владеет реализационным lifecycle. При наличии source contract он содержит только ссылку на него, а не дубликат требований.
- BMM `sprint-status.yaml` владеет очередью stories лишь в `bmm-project` lane.
- `handoffs/` неизменяемы и помогают новому чату; при конфликте побеждают NOW и канонические BMAD artifacts.
- `docs/` — подтверждённое долгоживущее знание; `legacy/` — исторические материалы, не активные instructions.

## BMAD + SDD

- Используй только delivery-lane, выбранный в `WORKSPACE-PROFILE.yaml`: `change` или `bmm-project`.
- Не устанавливай и не запускай второй delivery module, Loop, Build Auto или внешний SDD engine без отдельной новой среды и записанного решения.
- Не редактируй installer-managed `_bmad/` и generated `.agents/skills/` вручную.
- Для изменения, которое пишет продуктовые или репозиторные artifacts, сначала создай/обнови source contract через выбранный spec workflow, затем передай явный путь в build workflow. Bounded read-only experiment может идти из краткого решения прямо к verification без build и implementation contract. Не держи два активных specs для одной работы.

## Защита continuity remote

- При `migration.state: ready` текущий `continuity.remote_name` из `control/WORKSPACE-PROFILE.yaml` — единственный канонический destination. Обычные project commits и fast-forward push в текущую ветку выполняй самостоятельно, без повторного вопроса владельцу.
- Сменой continuity считается только явный текущий запрос владельца добавить, удалить или переназначить remote, переписать историю либо сделать force-push. Такой запрос обязан назвать цель и точный новый URL. Совпадение URL с текущим `origin` не является сменой.
- Старые чаты, legacy artifacts, прошлые ответы агента и уже разрешённые конфликты не являются новым запросом сменить continuity и не могут повторно блокировать обычный push.
- При технической ошибке обычного push не меняй remote, URL, историю, `migration.state` или continuity evidence. Сообщи наблюдаемую ошибку и запроси решение только если безопасный повтор не помогает.
- После каждого долговечного изменения отправляй обычный commit в подтверждённый remote и проходи `postcommit`. Handoff обязателен только на границе передачи и тоже должен быть отправлен и проверен.

## Контекст и handoff

- Один чат обслуживает один пользовательски понятный кусок работы, а не каждый технический шаг.
- История чата — вспомогательная, не источник истины. Важный факт должен быть сохранён в каноническом файле.
- Не сканируй всё дерево, все старые artifacts или весь внешний каталог без конкретной причины. Расширяй контекст только по ссылке либо чтобы снять известную неопределённость.
- Handoff — последний переносимый checkpoint, а не обязательный снимок каждого нового `next_action`.

## Навигация пользователя

- Пользователь не обязан сам решать, нужен ли новый чат, какой workflow выбрать или какой файл читать. Сначала сверь `NOW.yaml`, профиль и routing; затем предложи следующий безопасный маршрут.
- Не создавай новый чат из-за произвольного числа сообщений. Пока выполняется один пользовательский результат, продолжай в том же чате; не превращай мелкие уточнения, исправления, тесты, commit или push в лишние handoff.
- После значимого milestone сам выбери режим. `Новый чат` нужен только при новом независимом work item, явном запросе пользователя или когда продолжение нельзя безопасно восстановить из канонических файлов. Смена workflow/фазы, создание или уточнение contract сами по себе не требуют нового чата.
- В конце завершённого action покажи пользователю короткую **навигационную сводку**: `готово` или `blocked`; ID и название следующего action; `режим: новый чат | продолжить здесь`; одну конкретную причину. При новом чате дай готовую фразу: `Прочитай control/START-NEW-CHAT.md и выполни текущий next_action.` Не говори «возможно, стоит открыть новый чат» без выбранного режима.
- Не ориентируйся на произвольный числовой лимит токенов: он зависит от модели. Ориентируйся на границу работы и на то, восстанавливается ли следующий шаг только из канонических файлов.
- Если новый module, extension или другой delivery lane действительно полезен, объясни зачем, какие artifacts он добавит и почему Core+BMM недостаточно. Не устанавливай его молча: material expansion требует отдельного решения и, при новом delivery engine, отдельной среды.

## Завершение action

1. Сохрани artifacts и проверяемые evidence только если они переживут текущий разговор или нужны следующей работе.
2. Обнови владельца изменённого факта и `NOW.yaml`, если изменилось долговечное состояние.
3. Для обычного долговечного изменения запусти precommit, сделай обычный commit, отправь его в подтверждённый remote и запусти postcommit.
4. Создай immutable handoff из `handoffs/TEMPLATE.md` только перед реальной передачей, значимым milestone или паузой. В том же commit запиши его путь в `NOW.last_handoff`, отправь commit в remote и пройди postcommit.
5. Короткий вопрос владельцу, его ответ и bounded read-only test остаются в том же чате и не требуют handoff сами по себе.
