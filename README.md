# Универсальный шаблон рабочей среды Codex + BMAD + SDD

Это копируемая **рабочая среда для нового проекта на Core+BMM**, а не шаблон одного продукта или чата. Её можно продублировать для приложения, исследования, автоматизации, сайта, документации или существующего репозитория. Для специализированного delivery workflow создаётся отдельная среда, а не второй engine внутри этой.

Шаблон даёт четыре гарантии процесса:

1. В любой момент есть ровно одно следующее действие.
2. Новый чат работает по проектным файлам, а не по истории прежнего чата.
3. Один факт имеет одного владельца; нет двух конкурирующих backlog/state/spec.
4. Проверенный private Git remote и профиль установки делают среду воспроизводимой между аккаунтами и компьютерами.

## Как использовать

1. Скопируйте содержимое этой папки в новый пустой Git-репозиторий.
2. Прочитайте [tooling/INSTALL.md](tooling/INSTALL.md), примените `profiles/default-bmm.yaml`, заполните `control/WORKSPACE-PROFILE.yaml` и настройте continuity transport.
3. Выполните единственный начальный action из [control/NOW.yaml](control/NOW.yaml), используя [templates/INIT-001.md](templates/INIT-001.md).
4. После начальной настройки создавайте work через нативные BMAD artifacts, а не через второй самодельный SDD engine.
5. В каждом новом чате используйте [control/START-NEW-CHAT.md](control/START-NEW-CHAT.md).

Агент сам обязан сообщить, когда наступила настоящая граница работы: после значимого результата он выбирает `новый чат` или `продолжить здесь`, объясняет причину, называет один следующий шаг и при необходимости даёт готовую фразу для нового чата. Обычная правка, тест, commit, push или переход фазы не должны выталкивать тебя в новый чат. Тебе не нужно угадывать момент перехода.

## Что настраивается один раз, а что — для каждого проекта

| Один раз для себя | При каждом новом проекте |
| --- | --- |
| Твой личный `~/.codex/AGENTS.md`: язык, стиль общения, безопасность, Git-привычки | Копия шаблона, цель и границы проекта, private remote, реальный ID проекта |
| Базовый принцип Core+BMM и правила handoff | Чистая установка BMAD по тому же профилю и запись фактической версии |
| Навигационное поведение агента, уже записанное в project `AGENTS.md` | `INIT-001`, первый work item и первый handoff на реальной границе передачи |

Повторная установка BMAD не означает повторную ручную настройку всей системы: агент проводит её по одному профилю. Runtime намеренно не копируется между проектами, потому что он содержит project-specific paths и generated files; его перенос вернул бы stale cache и скрытые зависимости старой среды.

## Windows: короткий путь clone

Если в проекте есть старые глубокие папки с длинными именами, clone на Windows
делайте в короткий путь, например `C:\Projects\my-project`. Не используйте
глубокую временную вложенность: суммарный путь может превысить ограничение Windows.
Это правило относится к месту clone, а не к runtime: `_bmad/` и `.agents/`
по-прежнему устанавливаются заново и не передаются между проектами.

## Слои и владельцы

```text
Личные правила пользователя ──► ~/.codex/AGENTS.md
                                     │
Проектный Git-репозиторий ───────────┼──► AGENTS.md
                                     │        │
                            PROJECT-CHARTER  ▼
                                      \  control/NOW.yaml
                                       \       один action
                                        \          │
                                         ▼         ▼
                       BMAD source / implementation contracts
                           _bmad-output/…          evidence/
                                      │               │
                                      └─────► handoffs/ ───► новый чат только на реальной границе
```

| Факт | Канонический владелец |
| --- | --- |
| Личные межпроектные предпочтения | `~/.codex/AGENTS.md`, не репозиторий |
| Цель, границы и ограничения проекта | `docs/PROJECT-CHARTER.md` |
| Профиль среды, выбранный delivery-lane и способ восстановления | `control/WORKSPACE-PROFILE.yaml` |
| Ровно один следующий action | `control/NOW.yaml` |
| Состояние передачи work item | `NOW.active_work.dispatch_state`; правила — `control/STATE-MACHINE.md` |
| SDD source record и contract | `bmad-spec` workspace: `source_memlog` → `.memlog.md`; `source_contract` → производный `SPEC.md` |
| Реализационный контракт и его lifecycle | BMM `implementation-artifacts/spec-*.md` |
| Очередь большого продукта | BMM `sprint-status.yaml`, только после его создания |
| Долговечные подтверждённые знания | `docs/` |
| Доказательства | `evidence/`, tests/CI и ссылки из контрактов |
| Снимок передачи | `handoffs/H-*.md`, но не источник состояния |

Это не означает «всё в одном файле». Это означает один владелец каждого типа данных.

## Что BMAD и SDD делают здесь

- **BMAD Core + BMM** ведут workflow и создают нативные artifacts.
- **SDD** — дисциплина контрактов: сначала источник требований и решений, затем реализационный контракт, затем проверка. В базовом BMM-профиле эту роль выполняет `bmad-spec` с append-only `.memlog.md`.
- **NOW.yaml** — тонкий диспетчер между workflow и чатами. Он не дублирует status, список stories или требования.
- **Codex** — исполнитель ограниченного action. Его чат не является памятью проекта.

Подробная стыковка — в [control/ROUTING.md](control/ROUTING.md).

## Чего в шаблоне намеренно нет

- конкретного приложения, облака, базы знаний или продукта;
- старых `_bmad/`, `.agents/`, render-cache, user config или Git history;
- заранее включённых delivery-модулей, Loop, Build Auto, TEA, CIS или Builder;
- переписанных вручную generated skills;
- личных путей, секретов и transcript-логов чатов.

Интеграции подключаются только решением конкретного проекта и не становятся частью основы шаблона.

## Проверка готовности

Перед передачей работы или созданием нового чата запустите:

```powershell
./tools/verify-workspace.ps1
```

Он проверяет структуру, один исполнимый next action, существование его входов, profile Core+BMM и локальные файлы в Git. После `migration.state: ready` обязательны remote, restore evidence и последний переносимый handoff; validator проверяет этот checkpoint исторически, поэтому обычная работа не создаёт лишние handoff. Полные критерии — в [tooling/VERIFY.md](tooling/VERIFY.md).
